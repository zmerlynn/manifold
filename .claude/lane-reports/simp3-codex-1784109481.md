## Findings (ranked, with my verdict)

### 1. Filter-then-exact idiom repetition - ACCEPT WITH CAVEAT
src/overlap3.cpp:1013 (WindCrossTri), :1133 (PrecomputeSeedSign), :1610 (cleanPierce)

The two-line idiom `s = Orient3DFilterSign(...); if (s == 0) s = Orient3DExactSign(...)`
is genuinely repeated at these three sites (verified: cleanPierce uses
`s != 0 ? s : Orient3DExactSign(a,b,c,d)`, PrecomputeSeedSign the seed-side variant,
WindCrossTri four times). Extracting a `FilterThenExactSign(a,b,c,d)` helper is
bitwise-identical (same two calls, same order). Real, safe, modest.

CAVEAT (my correction): Codex's finding also lists :737 (EdgePiercesTri) and its
"After" sketch shows an `EdgeTriFilterThenExactSigns` helper. EdgePiercesTri does
NOT use filter-then-exact - it returns -1 on any filter-0 to hand the tie to the
SoS caller (EdgePiercesTriSoS). Folding EdgePiercesTri into a filter-then-exact
helper would make it escalate to exact instead of returning -1, silently changing
the SoS-handoff contract (a fail-closed-to-SoS boundary). So: extract the helper
for the three exact-escalating sites ONLY; leave EdgePiercesTri's filter-only -1
protocol exactly as is. The three predicates share STRUCTURE but three DIFFERENT
tie policies (filter-only / filter-then-exact / filter-then-SoS) - do not unify
the policies, only the identical filter-then-exact leaf.

### 2. Single- vs multi-component dispatch duplication - ACCEPT (medium confidence)
src/overlap3.cpp:2523 (parallel co[i] body 2536-2562) vs :2581 (sequential body 2582-2635)

Verified: both branches carry the identical gate -> Invalid-fail-closed ->
Clean-early-exit -> dirty -> ResolveComponent -> re-gate -> emit decision, once in

same firstFatal = first-in-order, same push order). The single-component path would
now allocate one CompOut - a trivial cost, bitwise-identical output. Care needed:
the reduction must stay strictly index-ordered and move semantics preserved.
