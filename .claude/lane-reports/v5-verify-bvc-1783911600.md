PHRASING OVERCLAIM (flag, not a kill): the reopen says exact winding gives paired
halfedges "BY CONSTRUCTION... the cross-edge coupling the DCEL provided for free, now
provided by exactness" (ExactArrangement3D:104-105). This conflates two things. The
June memo's durable result is that manifold output needs a GLOBAL DCEL with RADIAL
ORDERING of face-sides around each arrangement edge. Exactness provides (i) consistent
CLASSIFICATION (adjacent wedges agree on w_S) and (ii) PARITY (winding jumps sum to
zero => even number of boundary sectors around an edge). It does NOT provide (iii) the
radial ORDER itself - you still must sort the face-sides cyclically around each edge
to PAIR the IN/OUT transitions and to DETECT genuine non-manifold edges (>2 boundary
sectors). Exactness makes the radial-order PREDICATES exact (no FP ties in the cyclic
sort); it does not remove the DCEL. The doc's later "manifold by construction still
requires the COMPLETE EXACT ARRANGEMENT" partly recovers this, but "for free" oversells
it. RECOMMEND: say the radial-ordering DCEL is still required; exactness makes its
predicates tie-free, which is what cures the #3 disagreement.

## ATTACK 3 - B'S HONEST COST. VERDICT: cost story under-numbered; B and C are ONE variant with a scope dial.

BIT-LENGTH (real Havoc coords ~1.3e4). A double ~1.3e4 is an exact rational m/2^39,
m ~53-bit. orient3d = 3x3 determinant of differences: numerator ~3*54+3 ~= 165 bits
over 2^117 - a few machine words, Shewchuk-filtered to a double in the common case,
exact fallback ~165-bit. This is level-1 (predicate on INPUT). But building the
arrangement needs predicates on CONSTRUCTED points (order intersection points along an
edge; is a triple point inside a face) = level-2: inputs are ~165-bit rationals, a
degree-3 op multiplies bit-length ~3x -> ~500-bit numerators/denominators. Each
further construction level x3 again (level-3 ~1500-bit). So the honest per-construction
cost is HUNDREDS of bits after two arrangement levels, not "double-cheap". The doc's
"predicates on input data (doubles are exact rationals)" framing is only fully true at
level-1; a real arrangement reaches level-2 (~500-bit) in its internal ordering
predicates. Tractable (GMP eats 500-bit), but the doc should NAME it, and name the
mitigation it already implies: keep decisions as input predicates wherever possible so
bit-growth stays bounded; the cascade blowup is only avoided by NOT feeding constructed
coordinates back into further predicates.

VALIDITY GATE: the doc DOES name it (B verdict: "gated by Is2Manifold /
self-intersection", R3 elaborates snap-can-create-intersections). No overreach there.
ADDED RISK the doc misses: snap-rounding is treated as OUTPUT-only (R3). Cascaded exact
constructions may need INTERMEDIATE snapping to bound bit-growth, and intermediate
snapping can change TOPOLOGY, not just output coordinates - a stronger failure than R3
(output-only) admits. Worth a line in R3.

CLEAN-MODEL TAX + THE B==C QUESTION. Cray resolves at eps in ~16s. What does B cost
it? If B is a production WHOLE-MESH path, Cray's clean 16s eps resolve becomes a full
exact arrangement (much slower, for zero correctness gain - Cray is not degenerate). If
"B runs only when flagged" it IS C. So B is NOT a distinct shippable variant. There
are three B's hiding in the doc, and only their ROLES differ:
  - B-as-oracle: run offline on the corpus to VALIDATE C. Test-time cost, legitimate
    north star.
  - B-as-C's-fallback (stage 5): whole flagged COMPONENT C cannot bound-clean.
    Degeneracy-scoped = C's escape hatch.
  - B-as-production-whole-mesh: taxes clean models, input-scaling. The doc already says
    DO NOT ship this first - correct.
RECOMMEND: collapse the two-row table to ONE variant, "exact arrangement at scope S":
S=flagged-region = C (production, pays for degeneracy); S=whole-mesh = B (offline
oracle / the unbounded limit of C when R1 fails). They are the same mechanism with a
scope/role dial, NOT distinct algorithms. The doc's "C and B are the same object at two
scopes" is right; the SEPARATE variant rows with separate verdicts overstate the
distinction and let B's "input-scaling cost" read as a shippable-variant property when
it is only the cost of the offline-oracle / percolation-limit role.
