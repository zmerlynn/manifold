## Log

### Item 1 UNIFIED BROADPHASE - ABORTED (premise refuted; collider REGRESSES GT7081)

LOUD FINDING: both audits' #1 premise ("GT7081 spends 146s in the resolver's
O(F^2) AABB scans") is WRONG. Direct perf profile of GT7081:
- ~50% = the GATE's `IsSelfIntersecting` -> `DistanceTriangleTriangleSquared`
  (ALREADY BVH-backed core library code, out of this lane's scope).
- ~23% = `WindingAt` under `EmitCleanFaces` (the deferred winding-BVH axis,
  explicitly out of scope in both audits + the design doc).
- ~10% = `RecordSeams`; `DetectCoplanarClusters`/`SnapNearCoplanarClusters` are
  each ~1.5%. The resolver's three brute O(F^2) bbox scans total ~14%, and they
  are cache-friendly (sequential lo/hi arrays, branch-predictable early reject),
  ~2s each on the big components. siA/siB have a DIFFERENT profile: WindingAt is
  86% (they are single 17k-tri components).

STALENESS BUG CHECK (Codex caution): NO resolver scan uses collider_ today (all
brute-force), so there is no stale-collider bug at HEAD. It would only arise IF
one switched to the cached collider_ post-snap.

I still implemented the collider broadphase (`BroadphasePairs` helper: fresh
Collider from GetFaceBoxMorton, superset==brute set since faceBox==lo/hi and
Box::DoesOverlap==the old bbox lambda, sorted (i,j) to preserve seam ordering)
and routed Detect/Snap/RecordSeams through it. It is BITWISE-IDENTICAL (all 5
FNV hashes matched; GT7081 hash 15a2a2b6e33d3936 identical head vs item).

But a CONTROLLED back-to-back A/B (CPU time, robust to the 3x machine
contention) shows it REGRESSES GT7081:
- HEAD: cpu ~60s.  Sequential collider: cpu ~78s (+30%).  Parallel collider
  (tbb::combinable recorder): cpu ~83s (+38%), both rounds consistent.
Cause: GT7081 = 2 big dirty components (11656, 19352 tris) + 11 tiny 32-tri
clean ones; the collider BUILD overhead (GetFaceBoxMorton + Morton sort + tree,
repeated across ~8 scan-calls on the big components + 13 gate calls) exceeds the
cache-friendly brute loops it replaces, and the real bottleneck (gate ISI +
WindingAt, ~73%) is untouched so the change only makes the ~14% broadphase
WORSE. Parallel is worse still (thread-spawn + merge overhead; machine already
core-saturated).

Per the "nothing weakens" rail I cannot land a 30% GT7081 regression, and the
premise (dominant cut) is refuted. ABORTED - reverted overlap3.cpp to HEAD, FNV
restored to baseline. A genuine win here would require optimizing the GATE's
IsSelfIntersecting and the WindingAt query-BVH, both out of scope.

### Item 6 validated swaps (la::cross + Box::DoesOverlap) - LANDED

Re-verified bitwise: linalg cross(vec2) is exactly `a.x*b.y - a.y*b.x` (== the
hand-rolled `cr`; `-ffp-contract=off` in the build so no FMA divergence);
shoelace `p.x*q.y - q.x*p.y` == `la::cross(p,q)` (mul commutes bitwise); triangle
area `(p1-p0)x(p2-p0)` == la::cross of the vec2 diffs. Box::DoesOverlap is the
same 6 comparisons ANDed (reordered; finite coords, no NaN) as the hand-rolled
`!(hi<lo || ...)`.

Swapped: the two `cr` lambdas (TrianglesOverlap2D, PointInTri2D) + 4 area sites
(ExtractCells, loopArea, LargestSubTri, the EmitSeamedFace CCW check) -> la::cross;
TriSoup (lo/hi -> Box, BBoxOverlap = box[i].DoesOverlap(box[j])) and RecordSeams'
local lo/hi + bboxOverlap likewise. NOT the SegPlanePoint lerp (rejected, not
bitwise).

Validation: FNV all 5 IDENTICAL; 18 fold/gate/fail-closed pins green.
