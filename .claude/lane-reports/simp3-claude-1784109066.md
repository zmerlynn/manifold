## 1. cleanPierce is a hand-rolled duplicate of WindCrossTri  [PROVEN bitwise]

Site: src/overlap3.cpp:1610-1634 (the `cleanPierce` lambda inside RecordSeams'
phantom-seam guard).

The lambda re-rolls the 5-orient segment-vs-triangle straddle+interior test with
its own filter-then-exact `sgn` helper. That is EXACTLY what the shared
WindCrossTri predicate already does: for a=Tt0,b=Tt1,c=Tt2,p=u,seed=w the two
plane-side signs (da=su,db=sv) and the three edge-edge signs
(o1=orient(u,w,Tt0,Tt1), o2=..(Tt1,Tt2), o3=..(Tt2,Tt0)) are the SAME calls in
the SAME order with the SAME filter-then-exact completion. cleanPierce's
"strict-interior pierce" == "WindCrossTri decided (true) AND delta != 0":
 - endpoint on-plane (su/sv==0)        -> WindCrossTri returns false            (skip)
 - same side (su==sv)                  -> WindCrossTri true, delta 0            (skip)
 - crossing on tri boundary (o_i==0)   -> WindCrossTri returns false            (skip)
 - strict interior (o1==o2==o3)        -> WindCrossTri true, delta=+/-1 (nonzero)(hit)
delta != 0 whenever it returns via the interior branch (da!=db => dot(w-u,n)!=0).

Simplification: replace the 25-line lambda with a 3-edge loop calling
WindCrossTri (net ~-11 lines). Also REMOVES a hand-rolled exact-predicate
scaffold, folding it onto the one blessed WindCrossTri chain (kernel-tripwire
aligned). Coherence: the tripwire comment at overlap3.cpp:699 lists cleanPierce as
a direct Orient3DExactSign caller - after the fold it reaches the kernel only via
WindCrossTri (already a listed caller), so drop cleanPierce from that list.

expected-bitwise? YES - identical orient args/order/completion; delta sign is
computed but unused.
risk: LOW. Confined to the fail-closed nPts!=2 gate.
VALIDATION: applied in copy, rebuilt. ALL SIX hashes identical incl openscad
(same fail-closed counters). Full Overlap3 suite: 33/33 PASS. PROVEN.

## 2. Driver's single-component `else` branch duplicates the two-pass path  [PROVEN bitwise]

Site: src/overlap3.cpp:2523-2636. RemoveOverlaps3D splits on
`if (components.size() > 1)`: the >1 branch runs the two-pass parallel
gate/resolve/re-gate into a CompOut vector then reduces in index order; the else
branch re-implements the identical gate -> resolve -> re-gate -> counters logic
sequentially (57 lines).

For size 1, autoPolicy(1,1) runs the two-pass sequentially and the reduce yields
byte-identical counters, firstFatal, and output order (meshID is assigned once in
ComposeComponents, which returns std::move(parts[0]) for a single part - the
bitwise pass-through is preserved). So the else branch is deletable: drop the
`> 1` guard, run the two-pass unconditionally (net ~-55 lines).

expected-bitwise? YES for the only affected case (single component). Multi-comp
carriers already use the two-pass, unchanged by construction.
risk: LOW-MED (driver control-flow; more review surface than #1). ONE caveat: the
deleted else branch carries the fuller RE-GATE rationale comment ("verified
UNREACHED on constructible general-position fixtures... NOT demoted to
DEBUG_ASSERT"); relocate it to the surviving two-pass re-gate site (~2556) so the
rationale is not lost.
VALIDATION: applied in copy (on top of #1), rebuilt. Single-comp carriers
(PokedCube/siA/siB, all comp=1) + multi-comp all hash-identical; the
Dispatch/SingleComponent/MultiComponent/PassThrough pins: 9/9 PASS. PROVEN.
